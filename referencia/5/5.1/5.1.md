## T-M1-01 — Limitación de tasa multinivel y bloqueo progresivo

| | |
|---|---|
| **Escenario** | **ESC-M1-01**: 10,000 intentos por minuto; 0 cuentas comprometidas; mitigación activa en ≤ 60 s; < 0.1% de usuarios legítimos afectados. |
| **Táctica** | *Detectar ataques* (detección de intrusión y de denegación de servicio) + *limitar acceso*. |
| **Cómo se aplica** | El gateway limita la tasa por IP y por huella de dispositivo (token bucket en Redis). Keycloak exige CAPTCHA tras 5 fallos, bloquea la cuenta 15 minutos tras 10 fallos y notifica al titular. Los intentos se registran en la bitácora. |
| **Dónde se ve** | `api-gateway` (componente `RateLimiter`) y `keycloak` (6.2). |

### ADR-T-M1-01 — Dónde limitar los intentos de inicio de sesión

| Opción | Ventajas | Desventajas |
|---|---|---|
| A. Solo en Keycloak (detección de fuerza bruta por cuenta) | Ya viene incluida. | No frena el ataque distribuido sobre muchas cuentas: cada cuenta recibe pocos intentos. |
| B. Solo en el gateway (por IP) | Frena el volumen. | Una botnet reparte los intentos entre miles de IP. |
| C. WAF administrado (AWS WAF) | Reglas listas. | Costo adicional; menos control sobre la lógica por cuenta. |
| **D. Gateway (IP y dispositivo) + Keycloak (por cuenta)** | Cubre el ataque por volumen y el ataque por cuenta. | Dos configuraciones que mantener. |

**Criterios.** Medida de ESC-M1-01, falsos positivos, costo. **Decisión:** **D**; el WAF se reevalúa si aparecen ataques de capa 7 a gran escala. **Sustento:** cada nivel cubre la debilidad del otro. **Consecuencias:** los umbrales son configuración y se ajustan con la tasa de falsos positivos observada.

## T-M1-02 — Autorización en dos niveles con catálogo de permisos compartido

| | |
|---|---|
| **Escenario** | **ESC-M1-03** / ER-10: 100% de intentos de escalamiento rechazados, incluso con acceso directo a un servicio. |
| **Táctica** | *Autorizar actores*. |
| **Cómo se aplica** | El gateway valida firma y ámbito del token (permiso grueso). Cada servicio aplica un *guard* de NestJS de `@kipu/auth` que evalúa el permiso fino sobre el recurso (por ejemplo, `campaign:update` solo si la campaña pertenece a la marca del token). Ningún permiso se concede por defecto. |
| **Dónde se ve** | `api-gateway` y el paquete `@kipu/auth` usado por todos los servicios (6.3, 7.1). |

### ADR-T-M1-02 — Evaluación de permisos: gateway, servicio o ambos

| Opción | Ventajas | Desventajas |
|---|---|---|
| A. Solo en el gateway | Punto único de control. | Un acceso desde dentro de la red lo esquiva: incumple ER-10. |
| B. Solo en cada servicio | Control junto al recurso. | Lógica duplicada que diverge; tráfico inválido llega hasta los servicios. |
| C. Servicio central de autorización (por ejemplo, OPA como servicio) consultado en cada petición | Política centralizada. | Una llamada de red por petición (incumple ER-02). |
| **D. Dos niveles con librería compartida** | Cumple ER-10 sin llamada de red adicional. | Hay que versionar la librería. |

**Criterios.** ER-10, latencia (ER-02). **Decisión:** **D** (concreta ADR-M1-02). **Sustento:** única opción que cumple ambos criterios. **Consecuencias:** un cambio de permisos requiere publicar una versión de `@kipu/auth` y desplegar los servicios que la usan.

## T-M1-03 — Rotación de tokens de refresco con detección de reutilización

| | |
|---|---|
| **Escenario** | **ESC-M1-02**: revocación efectiva en ≤ 5 s; 100% de las familias de tokens comprometidas revocadas. |
| **Táctica** | *Revocar acceso* (reaccionar ante ataques). |
| **Cómo se aplica** | Token de acceso de 15 minutos y token de refresco rotativo de 30 días ligado al dispositivo. Si se presenta un token de refresco ya usado, Keycloak revoca toda su familia; M1 agrega los `jti` revocados a la lista de revocación en Redis y notifica al titular. |
| **Dónde se ve** | `keycloak` + `identity-service` + Redis del gateway (6.2). |

### ADR-T-M1-03 — Política de tokens de sesión

| Opción | Ventajas | Desventajas |
|---|---|---|
| A. Token de acceso de larga duración | Simple. | Un token robado sirve por días. |
| B. Token de refresco rotativo sin detección de reutilización | Reduce la ventana. | El atacante y el usuario pueden alternarse sin que nadie lo note. |
| **C. Rotación con detección de reutilización y revocación de la familia** | Al primer uso indebido se corta todo. | El usuario legítimo también debe volver a iniciar sesión. |

**Decisión:** **C** (soportada de forma nativa por Keycloak). **Sustento:** es la única opción que cumple la medida de revocación. **Consecuencias:** se acepta que el usuario legítimo deba volver a iniciar sesión tras un robo.

## T-M1-04 — Bitácora de auditoría de solo-anexado con encadenamiento de hash

| | |
|---|---|
| **Escenario** | **ESC-M1-04**: 100% de los accesos a datos personales trazables a un actor y un motivo; reporte de anomalías en ≤ 24 h. |
| **Táctica** | *Mantener pista de auditoría* (recuperación ante ataques). |
| **Cómo se aplica** | Toda operación sensible publica un evento en el tópico `audit.events`; `identity-service` lo persiste en `audit_log`, donde cada registro incluye el hash del anterior. La consola interna exige un número de caso para abrir datos personales. |
| **Dónde se ve** | `identity-service` + PostgreSQL M1 (6.2). |

### ADR-T-M1-04 — Dónde guardar la bitácora

| Opción | Ventajas | Desventajas |
|---|---|---|
| A. Tabla normal en la base transaccional | Simple. | Quien administra la base puede borrar registros: falla justo en el caso a cubrir. |
| B. Solo en la plataforma de logs | Sin desarrollo. | Retención corta; no tiene valor probatorio. |
| **C. Tabla de solo-anexado con encadenamiento de hash** (sin permisos de UPDATE ni DELETE) | Cualquier alteración se detecta. | Más almacenamiento. |

**Decisión:** **C**. **Sustento:** una bitácora solo vale si no la puede alterar quien tiene motivos para hacerlo. **Consecuencias:** la escritura es asíncrona; el productor exige confirmación del bus y reintenta.

## T-M1-05 — Validación local del token y circuit breaker por proveedor federado

| | |
|---|---|
| **Escenario** | **ESC-M1-05**: 0% de impacto en sesiones activas si Google o Apple caen; < 8% de inicios de sesión afectados. |
| **Táctica** | *Degradación*. |
| **Cómo se aplica** | Las sesiones activas no dependen del proveedor, porque el token se valida localmente con JWKS. Para inicios de sesión nuevos, un circuit breaker por proveedor (abre tras 5 fallos) oculta temporalmente ese botón y ofrece los demás métodos (OTP por celular o correo). |
| **Dónde se ve** | `identity-service` (componente `FederatedLoginGuard`). |

### ADR-T-M1-05 — Comportamiento ante la caída del proveedor federado

| Opción | Ventajas | Desventajas |
|---|---|---|
| A. Mostrar el error del proveedor | Simple. | Frustración; intentos repetidos. |
| **B. Ocultar el método caído y ofrecer alternativos** | El usuario siempre tiene un camino para entrar. | Hay que mantener dos o más métodos. |

**Decisión:** **B**. **Sustento:** cumple la medida sin infraestructura adicional. **Consecuencias:** el método OTP propio debe mantenerse siempre disponible.
